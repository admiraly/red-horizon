# Shared-authority playable client

The current client replaces the earlier prototype's private movement, ammo/reload timer and damage cone with the shared assembly player ABI. Local solo joins player0/front1. Each render collects normalized WASD direction, mouse yaw/pitch and fire/reload/sprint buttons; `player_input` stores intent and `sim_tick` advances the authoritative player once at30Hz. Only player records determine position, health, ammunition, reload, damage, suppression, death and safe redeployment. Held rifle cadence is4ticks (133ms), magazine30, reload60ticks (2seconds).

The renderer smooths camera correction at15/s, bounded to a visual interpolation factor0..1, and snaps on generation changes or corrections exceeding25m. This is camera smoothing, not movement prediction. Cosmetic recoil affects the rendered aim angle only. Shot/hit sequence changes drive the licensed shot playback and muzzle/hit feedback. The camera has no independent collision or health path.

Controls: WASD move, Shift sprint, mouse aim, left mouse held fire, R reload; Tab toggles the unpaused tactical view and free/captured cursor; F1/F2/F3 select a front and1/2/3 advance/hold/retreat; tactical left click sets a validated waypoint. Escape exits. The window title reports magazine, reload/down state, front/order, requisition/supply, operation state, health, suppression and remaining redeployment ticks. Green lower-left bar is health, amber bar is suppression; damage flashes a red lower edge and death shows a red redeployment bar and hides the weapon. Death requires no new key to recover at the authority's safe deployment.

All CPU player/camera/input orchestration remains NASM. CPU duplicate terrain math was removed. GLSL uses the shared terrain's exact ridge/bowl expression. Exported `terrain_obstacles` bounds/base/height drive five wall/bunker silhouettes, so rendered solid volumes match the authoritative static obstacles. The client can render all four connected player records using their64byte layout; the local player is hidden in first person and visible on the map. This does not yet establish network connectivity.

Exit telemetry retains `camera_x/z`, shots/hits, ammo/reload counts, front/orders and adds authoritative player HP/suppression/respawn/generation plus `start_player_x/z`. Use the actual start values for movement assertions. The public records and input contract are defined in `schemas/player.inc` and `docs/next-contracts.md`.

## Dedicated co-op client path

Use the dedicated assembly server and two copies of the actual renderer: `red-horizon-coop-server --port 7777`, then `red-horizon --connect 127.0.0.1 --port 7777`. `--help` prints controls and launch options. Server default lifetime is persistent; the owning user terminates it. Each endpoint receives its own player ID and company front. The title shows assigned ID/front, validated server tick, command state and explicitly labels the regional snapshot view. In this mode the units count is known living region records, not the full server army. The server continues simulating the entire operation independently of this view.

The client polls the actual UDP adapter, sends current normalized input intent at30Hz and never calls `sim_tick` or `player_input` in network mode. All four authoritative player records are rendered from snapshots; local first-person body is hidden and remote players use cyan silhouettes/map markers. Shared static terrain obstacles remain present even before region entities arrive. Region snapshots warm up incrementally and omit offscreen detailed actors; the tactical map is not a global intelligence feed. Timeout is shown as joining/connection lost; reconnect currently requires restarting the client.

Network camera preview is bounded to one fixed movement tick (at most0.3m), uses the shared terrain collision query and is disabled if no validated server tick advances for200ms, on disconnect, or while dead. It never changes replicated position or hit authority. Camera correction retains the same bounded visual smoothing. This is a narrow preview/reconciliation path, not full historical prediction or rollback.

Co-op command input requires the assigned company front; other fronts can be inspected, but orders show a readable ownership denial. A single queued order retries the adapter's busy state. Once sent, its parameters cannot be overwritten until the matching server ACK is consumed. Inputs wait during that outstanding command so the ACK status remains unambiguous. Only successful ACK publishes the goal marker, selected order mode and accepted-order counter. Rejected ACK preserves the last accepted marker/count. Goal markers represent this client's successfully acknowledged orders; remote company goals are not replicated. Simultaneously held command keys use separate edge latches to prevent repeat spending. Before this client has an accepted waypoint, advance selects its front's hostile column2 deployment site, or column3 command site if column2 is no longer enemy owned, from received site records; it does not converge the company on the human player.

### Two rendered clients: verified

`python3 tests/test_client_coop.py CLIENT SERVER` passed against the actual assembly server, adapter, player, terrain and current AI modules on a private Xvfb/software OpenGL display. It established players0/front0 and1/front1, read both distinct authoritative player records in both graphical clients, and sampled18 and24 cyan pixels respectively at the other player's actual tactical-map location. The captured `/tmp/red-horizon-v2-coop-player-0.png` and `-1.png` were visually inspected. The driver writes corresponding PPM artifacts using only standard-library conversion in subsequent runs.

Real WASD moved each server-owned player independently; held fire changed authoritative shots/ammunition and replicated those counters to the other client. SIGSTOP on the test-owned dedicated server left both clients' authoritative player records and simulation tick counters unchanged during input; exit telemetry reported `local_sim_ticks=0` for each. The host was resumed before continuing and terminated during cleanup.

The first advance key targeted the actual hostile front site and reached the server after successful ACK. An unowned-front click produced the ownership denial without changing that server goal. A valid owned waypoint reached (4994.375,3904.44409), spent exactly5 requisition after accounting for connected-site income, and published one accepted order after ACK. Setting the test-owned server's requisition to0 before another valid command produced a real rejected server ACK; the prior accepted server goal, client marker and accepted-order count remained unchanged. The driver restores the fixture funds afterward.

A positioned enemy encounter executed actual server attacks: player0 reached HP0/respawn30, both clients received the death state, and player0's own window showed DOWN. Safe recovery returned HP100 at (3780,30.5434,1300), generation1→2, then replicated to both clients. The test never writes player health. Controller override fields and actor placement are development encounter fixtures; the live assembly world advances combat and recovery.
