# Bounded operation prototype

`src/sim/operation.asm` adds twelve physical capture sites: four per front at x=1000/3000/5000/7000 and z=1300/3900/6500 metres. Two columns begin allied and two enemy. Site 0 is the allied command root; site 3 is the enemy command root. Columns connect along each front and matching columns connect between adjacent fronts. The graph has exactly twelve nodes and bounded reachability work.

Public Linux SysV ABI, all routines preserve nonvolatile registers and use caller-saved integer/SSE scratch:

- `sim_sites`: twelve records, stride 32: x f32 at 0, z f32 at 4, owner u32 at 8 (0 allied, 1 enemy, 2 neutral), capture i32 at 12, role u32 at 16 (0 command, 1 depot, 2 production, 3 deployment), connected u32 at 20, health u32 at 24, flags u32 at 28. Flags bit 0 marks allied command, bit 1 enemy command, bit 2 contested occupancy. Coordinates and graph are authored; storage remains stable. Health starts 1000; zero-health sites provide no capture or connectivity. No site damage API is implemented.
- `sim_requisition[2]`, `sim_supply[2]`: u32 balances and currently connected capacity, indexed by side. Supply is capacity, not ammunition or a spent resource.
- `sim_operation_state`: u32, 0 ongoing, 1 victory, 2 defeat, 3 final defense.
- `sim_spend(EDI=side, ESI=cost) -> EAX=0/-1`: rejects invalid side, zero cost and insufficient balance without mutation. Successful transaction subtracts exactly cost. Atomicity means execution in the single authoritative simulation thread; this is not a concurrent or network API. It does not create units or buildings.
- `operation_init()` and `operation_tick()` are internal integration routines called from accepted `sim_init` and each `sim_tick`. Tick evaluates only at multiples of 30, corresponding to one second at fixed 30 Hz. There are no allocations. Tests may call operation_tick directly after setting a fixture tick counter.

Capture scans all living entity records within 200 metres of each site, independent of camera state. Either side's exclusive presence advances capture by one unit per second toward −10 allied or +10 enemy. Presence from both sides pauses progress and raises the contested flag. No presence preserves progress. Owner changes only at the endpoint, so full hostile takeover takes twenty seconds. Dead entities cannot capture. Infantry, armour and artillery can capture; airborne actors are excluded; no squad ownership, LOS or intelligence model is involved.

Connected ownership paths must lead to that side's still-owned, healthy command root. Capturing an intervening corridor can isolate otherwise owned sites. Each connected site contributes 100 supply capacity. Every evaluation gives 10 requisition per connected production site and 3 per other connected site. Disconnected or destroyed sites give none. Income saturates at UINT32_MAX rather than wrapping. Initial capacity is 600 per side and requisition 100 per side. There is no hidden spawning, automatic inventory regeneration, supply truck or production implementation. Army rifle ammunition is finite; nearby eligible infantry can draw reserves from finite physical depots. Supply capacity is separate from consumable depot inventory. See infantry-ammunition.md and depot-ammunition.md.

Allied ownership of the enemy command root yields victory. Loss of allied command ownership first yields visible final-defense state. Thirty consecutive one-second evaluations without recovery yield defeat; twenty seconds of exclusive allied presence can recapture within that warning window. Restoration resets the warning count. Own-root loss takes precedence over victory if both roots change together. Victory and defeat are terminal result states; the current simulation continues ticking rather than freezing. Capturing an isolated enemy command still wins: logistics currently limits capacity/income, not capture eligibility.

Replay hashing extends the existing FNV state checksum with all 384 site bytes, requisition, supply, operation state and the private warning counter. This changes checksum values for earlier simulations while retaining entity schema ABI v1. Same-build replay tests pass; no saved snapshot migration exists.

## Verified evidence

`python3 tests/test_operation.py build/libsim.so` passes real-occupancy capture, dead/contested rejection, a three-road cut and restoration, connected capacity 900→300→900, connected one-second income 48→9→48, checked underspend/UINT32_MAX transactions, saturating income, enemy command victory, final-defense timeout to defeat, full allied recapture during the warning window, and operation checksum sensitivity/replay. Fixtures modify entity positions/health before executing assembly operation passes; the Python driver does not implement capture/connectivity logic. The existing baseline/stretch simulation/replay suite also passes with both assembly modules linked.

Build both `world.asm` and `operation.asm`; link both into headless/client and shared test library. `gcc -shared -Wl,-Bsymbolic world.o operation.o -o libsim.so` supports the ctypes fixture driver. Headless JSON now exposes operation_state, requisition and supply. These tests establish operation mechanics, not player-facing map UI, logistics AI, fair strategic balance, useful autonomous site attacks or a complete cooperative operation. Default armies initially concentrate near the middle; command sites require deliberate player/formation movement that remains future work.

Fresh operation-integrated throughput measurements (i7-1355U, seed 1, 600 ticks): 8192 units mean 1.614982 ms/p95 2.692413 ms, checksum af0b1a9bb614a3b9; 16384 units mean 3.988937 ms/p95 6.253351 ms, checksum 7b167ff1f24bb400. Entity casualties remain 559/947 and 1794/2038, respectively. Both default runs remain ongoing with supply600/600 and requisition880/460: default static site roles give the allied side three production sites, so initial income is asymmetric (39 versus18 per second). This is fixture tuning, not a balanced final economy. The focused suite also verifies enemy-command capture through 600 actual sim_tick calls, demonstrating the world-to-operation integration path.
