# Headless verification

Run the full suite without an existing desktop:

```sh
env -u DISPLAY -u WAYLAND_DISPLAY python3 tools/dev.py test --suite all
```

Requirements: NASM2.16.03, GCC/libc, Python3, GLFW3.3+, Mesa OpenGL4.5, ALSA, Xvfb, libX11, libXtst. Ubuntu packages are listed in the local CI workflow. Fedora Xvfb package is xorg-x11-server-Xvfb. The graphics harness starts only its own private Xvfb with displayfd, disables TCP listening, forces software rendering, uses ALSA null, and stops that server in finally. It never sends input to the user's display.

`--suite headless` runs simulation, operation, waypoints, terrain/LOS, tactics, authoritative players, replay/bounds, reload, audio, proof UDP and actual co-op/adapter, tool/dependency/frozen-source and asset checks without opening a window or GPU context. The actual terrain-loader test links the system OpenGL library but makes no GL calls. `--suite graphics` runs the actual assembled client, shader compilation, first-person/tactical frame export and XTest controls on the private software display. Individual suites: simulation, reload, audio, network, tools. `test --suite network --extended` additionally runs authoritative network death/redeployment and a real UDP0/50/100/150ms one-way delay matrix with jitter, loss and reordering; Python only relays packets or arranges encounter positions in its own child process. It never supplies player damage/health. Add --background for an immutable source snapshot, job ID/log/result; collect JOB_ID reports terminal status.

The real assembly client submits8192 entity instances and12site markers. The graphics test checks nonblank framebuffer output in both views and uses the actual input path to test movement, automatic fire/magazine exhaustion, R reload blocking/refill, front selection, tactical waypoint acceptance/outside-bound rejection and Escape. The Python driver contains no game simulation or renderer. Screenshots, process logs, software renderer information, frame/GPU-query telemetry and controls results are stored under runs/headless-graphics-*. Background jobs keep these under their frozen source runs directory.

Profiler: src/render/metrics.asm uses a bounded8query GL_TIME_ELAPSED ring without blocking for query completion, and monotonic CPU wall samples (up to10000 each). CPU sample covers event/input/simulation/draw/swap work; the final screenshot sample also includes readback. GPU sample covers submitted render work; outstanding last queries are omitted. CPU includes swap pacing, not isolated CPU occupancy. Counters distinguish CPU/GPU sample counts. These are raw smoke measurements, not1080p reference-machine budgets, dense-hotspot performance, or particle/audio benchmarks. Actual hardware and software runs must remain separate.

## Fast iteration

`python3 tools/dev.py test --suite fast` runs128-actor actual combat/replay and side-swap outcomes, CLI/fixed-tick validation, plus existing operation, waypoint, terrain, player, tactics, reload/audio and asset checks, including fixed-size terrain-pack rejection and smooth cosmetic weather state. It omits sustained8192/16384 combat, UDP transport/faults, actual graphics and tooling isolation. Full `all --extended` retains all earlier coverage and also runs the small combat check. Focused operation/waypoints/terrain/player/tactics suites reuse the same actual core library.

Builds use NASM's transitive dependency output with the actual ELF/debug/include flags, including incbin files. Compiler bytes and flags participate in object fingerprints. Shader edits rebuild only the shader object; changed nested includes rebuild only their users. `--objects-only` performs assembly without linking (no GLFW/OpenGL dependencies), so it is useful for quick client syntax/dependency checks but does not validate GLSL or rendering. Failed assembly preserves the prior valid object/executable and still returns failure. Build-tool tests verify dependency propagation, source preservation, and immutable background jobs.

During feature work, use the fast or focused check after edits. At integration/publication checkpoints launch full extended checks with `--background`, keep independent work moving, then reconcile the frozen revision before publication. GitHub Actions still runs full extended coverage, preceded by a fast failure gate.
